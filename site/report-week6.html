Week 6 — The Model Baseline Analysis Tool

Week 6 July 14, 2026 ProgressResearch

Weeks 3–5 measured only whether a vision model can copy a puzzle back as data — that is perception, not problem-solving. This week we built the instrument to separate the two: a single, self-contained tool that measures, for any model, whether it can solve a puzzle blind, reconstruct it, and solve it from its own reconstruction. No new research claim this week — the deliverable is the measuring device and a clean baseline reference point for everything that follows.

In Plain Terms

Everything up to now has asked one question: can an AI look at a picture of a colored-grid puzzle and faithfully copy it back as data? That is about seeing. But these puzzles are meant to be solved — you study a few before/after examples, infer the rule, and apply it to a new grid. This week's tool measures three different things for any model: (1) can it solve the puzzle cold straight from the image; (2) can it copy the puzzle back as data (what we've measured before); and (3) if it copies the puzzle first and then solves from its own copy, does that help or hurt? Lined up, those three give a clean baseline of what today's models can actually do — and a reusable instrument for testing why.

Why Now

Weeks 3–5 established one robust fact: current vision models read MARC puzzle structure perfectly but read colors only partially (~50–80%), across model families. Every one of those numbers is a perception score — how faithfully the model reconstructs what it sees. We had never measured whether any model can solve a puzzle at all.

Before going further, we wanted to cleanly separate two things that reconstruction scoring tangles together: can the model see the grid, and can it reason to the answer? A model could see perfectly and still fail to solve, or mis-see yet still infer the rule. The only way to know is to measure solving and perception independently, then measure what happens when you chain them.

The Three Measurements

1 · Blind solve

Hand the model only the puzzle image (train pairs visible, test answer hidden) and ask it to produce the test output grid directly. No reconstruction step. Scored against the known answer.

2 · Reconstruction

Ask the model to copy the visible puzzle back as JSON. Scored on cell fidelity over what it can actually see (train grids + test input) — exactly the perception metric from prior weeks.

3 · Reconstruct-then-solve

A two-step chain: the model first reconstructs the image to JSON, then solves the puzzle from its own reconstructed JSON (text only, no image). This exposes how perception errors propagate into solving.

What We Built

A single self-contained HTML page — the Model Baseline Analysis tool — that runs entirely in the browser against MindRouter, with no server or build step. It renders the puzzle to an image client-side (same ARC palette, legend, and hidden-test-output "?" as our Python pipeline), so the model sees exactly what prior weeks fed it. Highlights:

  • Live model picker — the dropdown is populated from GET /v1/models on the cluster, so you always choose from what's actually available; you can also type a custom id.
  • Streaming requests — server-sent events with the per-model shaping settled on in Week 4 (thinking flag only for Qwen, JSON-object mode otherwise, no-retry on 404).
  • Two-sided scoring — solving is graded by exact match (whole answer grid, the ARC standard) and per-cell accuracy; reconstruction is graded on visible cells only (train grids + test input), cleanly separating perception from solving.
  • Visual diffs — the model's grids sit side-by-side with the truth, wrong cells outlined in red, with reasoning traces and raw responses tucked into expandable panels.
  • Portable logs — every run is saved in-browser and can be downloaded as a JSON log and reloaded later to review, so results don't live only on one machine.

How to Run It

The tool runs locally — it is not hosted on this site, because it calls the MindRouter cluster through a local proxy and requires an API key.

  1. Start the local proxy once — uv run code/scripts/cors_proxy.py. Browsers can't call MindRouter directly (no CORS header), so this small stdlib proxy forwards requests and adds the header; it also injects your key from keys.txt, so the API-key field can stay blank.
  2. Open code/tools/model-baseline-analysis.html (locally, or serve site/ with python3 -m http.server) — the base URL defaults to the proxy at http://localhost:8811/v1 and is remembered in your browser.
  3. Click Refresh models and pick a model; toggle thinking mode if you want it (Qwen-only, off by default).
  4. Choose a puzzle JSON file from code/puzzles/; the rendered image preview shows exactly what the model will see.
  5. Press Run all three — blind solve, reconstruct, and reconstruct-then-solve run in sequence and the scored results appear as a card.
  6. Download the log to keep results, or Load a previous log to review past runs — logs are portable JSON, so results don't live only on one machine.

Scope

To be clear about what this is not: we are not yet starting the core MARC research question (does the metaphor clue help models solve?). This week is about building the measuring instrument and getting a definitive capability baseline — solve, reconstruct, and reconstruct-then-solve — so every later experiment has a clean reference point.
